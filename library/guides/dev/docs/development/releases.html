Releasing KetraTerm

VERSION on master is the release version for libraries and the standalone app. Set it to the desired version and merge the change before releasing. No manual tag or version input is needed. The IntelliJ plugin owns its version and release workflow in its separate repository.

In GitHub Actions, select Release, then Run workflow on master. The workflow:

  1. Reads VERSION and compares it with all published GitHub releases, including prereleases. An already published version is skipped; a downgrade or an alias of an existing version fails.
  2. Validates finalization of the leading Unreleased heading in the library and standalone changelogs with the version and the current UTC date. Older entries and already finalized dates are preserved. A finalized section with additional Unreleased changes is rejected to avoid ambiguous release contents.
  3. Looks for a successful full Test Suite run with a validation record matching the source Git tree, including build and workflow files. The lookup checks the latest 30 successful runs; missing or expired evidence requires full validation.
  4. Reuses matching source validation, allowing only the release tool's deterministic changelog finalization. Without matching evidence, runs the full CI validation set on the pinned source commit, including native/desktop suites and three-platform consumers. A failure creates no new tag; fix the source and rerun with the same VERSION.
  5. Finalizes the changelogs from that validated commit, commits them to master, and creates v{version} in one atomic push. If master advances during verification, the push fails; rerun against the updated branch. Existing tags are never moved, and retries continue to validate and publish their pinned contents.
  6. Checks release-mode Maven artifacts and consumers, validates native version metadata, publishes Maven artifacts, builds application binaries, and creates the GitHub release with notes from both versioned changelog sections. Relative links in those notes point to the tagged source.
  7. Triggers website/documentation publication through the workflow_run hook after successful completion, so downloads reflect the published assets. Tags and GitHub release events do not trigger extra deployments. Relevant master pushes still publish development documentation; changelog-only edits publish with the next relevant push or successful release, or manually.

publicationChecks remains the full local prepublication check (formatting, ABI, JVM tests, consumers, and artifact metadata). Remote publishing depends on the narrower publicationArtifactChecks: source validation is the release workflow's responsibility, while release-mode consumer and artifact checks run in the same Gradle invocation as publication. No ordinary JVM tests are repeated just to upload.

Release bot setup

The release commit and tag are pushed as a dedicated GitHub App. Create and install the app on this repository with Contents: Read and write, then add it to the master ruleset's bypass list with Always allow. Save the ruleset. If release tags have their own ruleset, allow the app to create those tags too. Other contributors continue to follow the existing branch rules.

On the app's General settings page, copy its Client ID and generate a private key. In the repository's Settings > Secrets and variables > Actions, add:

  • Variables: RELEASE_APP_CLIENT_ID containing the app's Client ID.
  • Secrets: RELEASE_APP_PRIVATE_KEY containing the entire downloaded PEM file, including its BEGIN/END lines.

See GitHub's App authentication guide. The workflow validates these credentials before the release build, generates a token scoped to this repository with contents-write permission, and uses it only for the atomic commit/tag push. The token is revoked at the end of the job. Ordinary checkout and release API calls use GITHUB_TOKEN; they do not inherit the release app's bypass access. Existing Maven Central and signing secrets are still required.

At the start of the next development cycle, bump VERSION to the next intended release and add a new ## [Unreleased] section to both changelogs in the same change, before adding new release notes. Development builds append -SNAPSHOT to VERSION; keep that suffix out of the file itself.

Prereleases

Use the native packager's existing formats: 0.5.0-alpha01, 0.5.0-beta02, or 0.5.0-rc01. Stage numbers are 1–19; unpadded forms such as alpha1 are also accepted, but cannot be published alongside their padded aliases. The order is alpha, beta, rc, then stable, with numeric ordering within a stage (alpha2 precedes alpha10). Dotted suffixes (alpha.1), unnumbered stages, build metadata, and -SNAPSHOT are rejected before publication. Prereleases are marked as such on GitHub and never become the latest stable release. A subsequent 0.5.0 release is newer than 0.5.0-rc19.

Interrupted releases

Use GitHub's Re-run failed jobs to resume after a publishing failure, preserving successful Maven publication. Maven releases are immutable; do not rerun a successful Maven upload unnecessarily. If preparation is rerun with an existing unpublished tag, it checks out and validates that tagged commit, preserving its files and date rather than releasing newer changes on master. Tags containing unfinalized changelogs are rejected.

Run the release automation tests locally with:

node --test .github/scripts/release.test.mjs
