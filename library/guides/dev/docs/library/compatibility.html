Library compatibility

KetraTerm's published libraries support Kotlin and Java hosts. Releases within the 1.x series preserve supported source, binary, and documented behavioral contracts. Experimental APIs follow their separate policy. The 0.x releases preceded this compatibility commitment; their migration notes remain below.

Supported boundary

Offering Published JVM modules
Headless pipeline protocol, parser, core, host, input, render-api, render-cache, transport-api, session
Swing view ui-swing
Local processes and shell metadata pty, shell-integration, shell-launch

Swing host controls ui-swing-host

Names have the ketraterm- prefix. The constraints-only BOM and dependency-only headless/Swing entry points are additional metadata publications. Use one KetraTerm version throughout the dependency graph; see installation and Maven setup.

Public/protected declarations in published libraries are supported contracts, except APIs explicitly marked experimental. Kotlin internal/private declarations are excluded, except published inline bridges that already-compiled callers can reference. App, testkit, benchmarks, and IntelliJ product implementation APIs are outside the supported publication boundary.

Kotlin 2.4 and JDK 25 are the minimum supported consumer versions. The build uses Kotlin 2.4.21, JVM target 25, and JVM default-method compatibility bridges. Consumer checks exercise Kotlin 2.4.0/2.4.21 and both Gradle metadata and POM-only resolution. A host replacing dependencies with a platform runtime must verify that runtime separately.

The headless entry point and its complete runtime dependency closure operate without java.desktop or frontend SDKs, including PNG decoding. Frontends consume neutral render data and own their graphics resources. Publication checks verify this boundary using both Gradle metadata and POM-only resolution.

Evolution rules

These rules apply to supported APIs within a stable major version.

  • Preserve JVM signatures, Kotlin metadata, defaults, and documented semantics.
  • Preserve constructor, copy, component, and default-call shapes of value data classes. Adding a defaulted constructor field can still break binaries.
  • Grow configurable snapshots through their existing builder/update entry points; preserve existing property types and defaults.
  • Preserve overloads and Kotlin default-call methods. Java overload generation does not make Kotlin default-argument changes binary compatible.
  • Treat interfaces as implementer contracts. New abstract members and new enum/sealed variants need source and compiled-consumer assessment.
  • Preserve public packed values, encoded enum order, constants, and inline bridge behavior; signature checks cannot detect semantic drift.
  • Keep public dependency types available through publication metadata.
  • During a stable major version, deprecate with a replacement before removal; incompatible removal belongs in a new major release.

OSC 22 sink migration

This migration applies to external sinks compiled before OSC 22 support in 0.x. Implement setPointerShape(TerminalPointerShape?); null restores the host pointer default. Recompile those sink implementations and Kotlin delegates.

OSC 21 color migration

This migration applies to custom implementations compiled before OSC 21 support in 0.x. Affected TerminalCommandSink implementations must implement applyColorRequest(TerminalColorRequest) and consume the borrowed batch synchronously. Custom TerminalModeController implementations must implement applyColorRequest(TerminalColorRequest, Boolean) with ordered mutations and permission-controlled replies. Recompile these implementations and Kotlin delegates. Existing palette constructor and copy signatures remain available.

The 0.x color-stack additions also require pushColors() and popColors() on both interfaces. Recompile affected implementations and Kotlin delegates; the core methods follow the color-stack contract.

Verification and baseline changes

Supported modules use explicit API mode and checked-in ABI snapshots. Published consumer fixtures compile and run independent Java/Kotlin clients; retained binaries test upgrades without recompilation. Deliberate linkage-failure controls check that the upgrade harness detects missing symbols.

./gradlew publicationChecks runs the library publication gates against a local repository without uploading. The consumer fixture guide explains individual checks and baseline refreshes. A deliberate development baseline refresh must record the break and migration; it cannot be presented as proof of compatibility with the earlier API or retained clients. A baseline refresh does not authorize breaking a supported contract within a stable major version.

ABI checks do not establish threading, lifecycle, coordinate, or protocol correctness. Those require semantic tests and the module contracts. Product release verification remains separate; see the gap map.

Experimental completion models

Completion and suggestion APIs remain experimental in 1.x. The ExperimentalTerminalCompletionApi and ExperimentalShellSuggestionsApi markers identify these APIs. They can change before stabilization, including their source and binary contracts. This exception applies to Java and Kotlin consumers. See the completion stability policy.

Earlier model changes preserved Java constructor overloads but changed Kotlin default-constructor and copy signatures. Recompile consumers affected by those changes. Custom engines and providers must honor the request's includeCommandNames flag for parameter-only completion.

The 0.x parameter-only request change deliberately refreshed only the retained completion client, with reviewed sources, ABI snapshots, artifacts, and provenance. Other baselines remain unchanged. These clients verify subsequent upgrades; they do not establish binary compatibility with earlier experimental models.

Color-reset and change-report baseline decision

The 0.x color-reset and mode 2031/2048 migration deliberately established a new retained-client baseline. Existing method signatures remain available, but the required additions to TerminalCommandSink, TerminalModeController, TerminalResponseChannel, and TerminalBuffer change their implementer contracts. Retained pre-feature Kotlin by delegates do not contain forwarding methods for these additions: the Swing consumer fails with AbstractMethodError when host assembly calls setChangeNotificationsAllowed.

When migrating from that earlier API, recompile Kotlin delegates even when their source is unchanged. Affected implementations must implement the new reset, subscription, notification-permission, and pixel-aware resize methods. These methods enforce terminal semantics and host authorization; they have no silent fallback defaults.

The chosen development migration records clients compiled against the reviewed new interfaces, with fixture sources, jar hashes, compiler/toolchain details, and staged dependency hashes in their provenance. Review sources, artifacts, provenance, and ABI snapshots together, then run the source-consumer and retained client checks described in the consumer guide. The refreshed baseline verifies subsequent upgrades of those recompiled clients; it does not establish binary compatibility with the pre-feature baseline or any earlier 0.x release.

Development migrations

This section records migrations from APIs that preceded 1.0. These changes do not require recompilation when upgrading supported APIs within 1.x.

Selection and text color rendering have explicit host policies. Existing JVM entry points remain available. Explicit selection fills are exact. The default minimum contrast ratio is 3.0. Faint text blends toward its displayed background. See color customization and migration for selection styles and contrast settings.

These earlier 0.x changes require affected consumers to recompile. Detailed release history remains in the changelog.
